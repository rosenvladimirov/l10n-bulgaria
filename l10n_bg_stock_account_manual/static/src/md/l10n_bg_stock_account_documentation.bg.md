# 📦 Ръководство — Автоматично складово счетоводство (България)

Модул **l10n_bg_stock_account** — автоматични счетоводни записи при валидиране на складов документ (picking) за продукти с **ръчна/периодична** себестойност.

## 📘 Какво прави модулът?
Стандартно Odoo 19 създава счетоводни записи при движение на стока **само** за продукти с `real_time` (перпетуална) себестойност. Българските фирми, които водят склада на **периодичен** принцип, не получават статия при приемане на стоката.

Този модул запълва празнината: позволява на **избрани продуктови категории** да генерират счетоводна статия при валидиране на picking, по българския стандарт:

```
Dr. Складова сметка (302/303/304)
    Cr. Сметка за складова разлика / транзит (301 / GRNI)
```

…без да се сменя `property_valuation` на категорията на `real_time`.

## ⚙️ Настройка (по продуктова категория)
**Inventory → Configuration → Product Categories → [категория]**, раздел със складовите сметки:

| Поле | Роля | Пример |
|---|---|---|
| **Auto-post stock accounting on validate** | Включва автоматичното осчетоводяване при валидиране на приемане | ✔ |
| **Stock Input Account** | Транзитна сметка, кредитира се при приход (дебитира се при фактурата) | 301 |
| **Stock Output Account** | Сметка за изписване/COGS при изходящ move | 702.100 |
| **Stock Loss Account (брак/липси)** | Дебитира се при брак или отрицателна инвентаризация | 669.200 |
| **Stock Gain Account (излишъци)** | Кредитира се при положителна инвентаризация | 709.000 |
| **Price Difference Account (+)** | Clearing при фактура > PO цена (за `l10n_bg_stock_price_diff`) | clearing |
| **Price Difference Income (−)** | Приход при фактура < PO цена | 709 |

> Полетата са **company-dependent** — задават се отделно за всяка фирма. Ако сметка липсва, системата прави fallback: Loss → Output, Gain → Input, Input → складовата разлика.

## 🧾 Поток на работа

### Приемане (Receipt)
1. Категорията на продукта има включен **Auto-post**.
2. Валидирай приемането (**Validate**).
3. Автоматично се създава статия: **Dr. складова (302) / Cr. Stock Input (301)**.
4. По-късно при осчетоводяване на фактурата 301 се дебитира срещу доставчика.

### Изписване (Delivery / consumption)
1. Изходящ move на продукт с Auto-post категория.
2. Статия: **Dr. Stock Output / COGS (702.100) / Cr. складова (302)**.

### Брак / Инвентаризация
- Брак или **отрицателна** корекция → **Dr. Stock Loss (669.200) / Cr. складова**.
- **Положителна** корекция (излишък) → **Dr. складова / Cr. Stock Gain (709.000)**.

> ⚠️ Без отделна Loss сметка бракът се осчетоводява по Output (COGS) — счетоводно неточно (брак ≠ реализирана продажба). Затова задай 669.200.

## 🔗 Преглед на генерираните статии
В самия picking има поле/бутон **„Account Moves"** (`l10n_bg_account_move_ids`) — показва свързаните счетоводни статии. При една статия отваря директно нея, при няколко — списък.

## 🤝 Връзка с ценови разлики
Заедно с **l10n_bg_stock_price_diff**: когато фактурната цена се различава от PO цената, разликата минава през **Price Difference Account (+)** (clearing, разпределя се по производствената верига) или директно в **Price Difference Income (−)** при по-ниска фактура.

## ❓ Чести грешки
- **Не се появява статия** → провери дали категорията има включен **Auto-post** и попълнена складова сметка за текущата фирма.
- **Брак по COGS** → задай **Stock Loss Account** (иначе fallback към Output).
- **Дублирани статии** → не комбинирай Auto-post с `real_time` valuation на същата категория; Auto-post е за manual/periodic.
- **Грешна фирма** → сметките са company-dependent; провери че са зададени за правилната фирма.

## 🔗 Свързано
`l10n_bg_stock_price_diff` (ценови разлики), `stock_account` (база). За ДДС/фактуриране виж ръководството *ДДС администрация*.
